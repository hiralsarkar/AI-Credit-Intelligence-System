Credit risk, data science and decisioning

I built a credit engine that approves more good borrowers and fewer bad ones.

Most lenders start with a bureau-score cutoff. It is simple, and it leaves money on the table: good applicants get turned away, risky ones get priced like safe ones, and the analyst gets a number with no reasons. This system replaces that cutoff with four models, one explainable decision, and a workbench an analyst actually enjoys using.

The problem

Four things go wrong when a lender decides on a bureau score alone

I framed every module around a question a credit committee actually asks. Each one has a measurable cost if you get it wrong.

Good borrowers get declined

A generic score ranks risk coarsely, so the cutoff turns away people who would have repaid.

Loans are priced blind

  2. Behavioural red flags: analyst review
  3. Concentration risk: analyst review
  4. Rate below breakeven: reprice
  5. PD under 10% and RAROC above 14%: approve
  6. Value-destructive: decline
  7. Everything else: analyst review

Self-audit

I audited my own engine and fixed what I found

Reading my engine line by line, I found that RAROC was always computed at a fixed 12% rate, whatever the loan was priced at. So a teaser-rate loan looked as profitable as a fully priced one. The current engine fixes that and five other issues, with tests that keep them fixed.

RAROC at the rate actually offered

The engine prices each loan at its offered rate and solves for the breakeven rate that just meets the 14% hurdle.

Before: fixed 12% revenue, so RAROC was really a second PD cutoff at about 16.7%.

Reprice by economics

A loan below breakeven is repriced to the higher of breakeven and the market grade rate, rounded up to 25 bp. Above the 24% ceiling it declines.

Before: repriced only when Module C said so.

Honest thin-file handling

New-to-credit applicants are scored on Module A alone, with a data-gap reason and an analyst review instead of an automatic decline.

Before: showed an invented 6.7% behavioural PD in the narrative.

Every decision has reasons

Every route records its own reason code, and a test checks 1,000+ input combinations to prove no notice is ever empty.

Before: one decline path could produce an empty adverse-action notice.

"What would change this"

Each non-approval states the smallest change that moves it: the PD needed, or the rate needed.

Before: decisions explained the past, not the path forward.

One source of truth

All thresholds come from one constants file. The recommended operating point has one shared definition, and the pipelines now run on Mac and Linux, not only Windows.

Before: hard-coded literals, 62.6% vs 61.9% in different outputs, backslash-only paths.

In an interview

How I talk about this project

The 30-second version

"Lenders often start with a bureau-score cutoff. I built four models on real public data and a decision engine that combines them. At the same default rate it approves 27% more applicants, and at the same volume it cuts defaults by 20%. Then I audited my own engine, found it ignored the loan's interest rate when judging profitability, and rebuilt it so every decision is priced, explained and tested."

The two-minute walkthrough
  • Problem: a generic cutoff mis-ranks risk and ignores price and lifetime loss.
  • Approach: one model per lending question, each beaten against a simple benchmark.
  • Decision: a 60/40 composite PD, then ordered rules ending in a 14% RAROC hurdle.
  • Result: the swap-set frontier, and 61.9% approval at 3.61% default.
  • Rigour: I found and fixed my own pricing flaw, with tests that keep it fixed.
  • Limits: four datasets, so the integration is a reference design.
Why 61.9% and not the income-maximising 63.7%?
63.7% is where income peaks while default stays inside the 3.69% appetite, but it sits exactly on that limit. I recommend one step inside, where the model beats the benchmark on approval and default at once. That leaves room for model error and economic drift, and it is easier to defend to a credit committee.
How did you choose the 60/40 weighting between Modules A and B?
A and B are trained on different populations, so there is no joint label to fit the weights on. I made it a documented governance choice: A is primary because it exists for every applicant, B is an overlay. I ran a sensitivity analysis and recorded the rationale in the governance folder, to be revisited on any retrain.
What was the most important bug you found?
RAROC used a fixed 12% revenue rate. That made profitability a function of PD only, so a loan offered at 6.5% looked as good as one at 12%, and repricing could never change the numbers. Now the engine prices at the offered rate and solves for breakeven. Karan's teaser loan used to be approved at 9% real RAROC; it is now repriced to 7.00%.
Is the collections uplift result causal?
No, and I say so in the code and docs. Loan modification was not randomly assigned, so the uplift is observational. I use it to compare targeting strategies, and I state that a randomised holdout is needed before it informs budget or capital.
How would you take this to production?
Score all four modules on one joint book, refit the composite weights on a shared label, add PSI drift monitoring with the amber and red triggers already in the constants file, run a randomised champion/challenger for collections, and wire the engine behind an API that writes to the audit log already in the code.
Scope

What this does not claim

  • The benchmark is a bureau-score cutoff, not a mature lender's production scorecard.
  • The four modules use four unrelated public datasets, so the combined engine is a reference design, not one book scored end to end.
  • Credible IFRS 9 staging lives in Module D on the Freddie Mac panel. Staging shown at origination is illustrative.
  • Capital is set at 10.5% of risk-weighted assets, which makes single-loan RAROC look high. The ranking of decisions is what matters.
